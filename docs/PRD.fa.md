# Kargah — سند نیازمندی محصول (PRD)

نسخه ۰.۱ (پیش‌نویس) · ۲۰۲۶-۱۱-۰۵ · وضعیت: برای بازبینی مالک

## ۱. خلاصه

**Kargah** (کارگاه) همان devchain است که به یک plugin قابل‌استفاده‌ی مجدد برای Claude Code تبدیل می‌شود و در یک ریپوی open-source جدا نگهداری می‌شود. هدف این مرحله: **بسته‌بندی چرخه‌ی فعلی `/plan ← /build` به‌صورت plugin، تثبیت قرارداد بین plugin و پروژه، و اضافه کردن مکانیزم اندازه‌گیری و بهبود بر پایه‌ی داده (`log.jsonl` و `/retro`).**

در این مرحله اسکلت‌های پروژه (template) ساخته نمی‌شوند. فقط قراردادی تعریف می‌شود که template ها بعداً باید رعایت کنند.

## ۲. زمینه و مسئله

devchain v1 در یک پروژه کار می‌کند ولی:

- دستورها، agent ها، hook ها و اسکریپت‌ها داخل ریپوی همان پروژه هستند. برای پروژه‌ی دوم باید کپی شوند و باگ‌فیکس‌ها بین پروژه‌ها همگام نمی‌ماند.
- هیچ داده‌ای درباره‌ی کیفیت اجرا ثبت نمی‌شود. بهبود فقط با پرسیدن «مشکلی بود؟» از Claude انجام می‌شود که قابل‌اعتماد و قابل‌مقایسه نیست.
- مالک یک نفر است، منابع سرور محدود است و ابزار issue tracker وجود ندارد؛ پس هر مکانیزم جدید باید سبک و فایل‌محور باشد.

## ۳. اهداف و غیراهداف

### اهداف (این مرحله)

- G1: نصب Kargah روی هر پروژه با یک دستور، بدون کپی فایل‌های devchain در پروژه.
- G2: قرارداد نسخه‌دار و مستند بین plugin و پروژه.
- G3: ثبت خودکار و قطعی یک رکورد برای هر package در `.kargah/log.jsonl`.
- G4: دستور `/retro` که از لاگ و git، حداکثر ۳ تغییر رتبه‌بندی‌شده پیشنهاد می‌دهد.
- G5: مهاجرت devchain v1 به Kargah بدون تغییر رفتار اصلی `/plan` و `/build`.

### غیراهداف (این مرحله)

- ساخت template های copier (base، api، ui، core).
- UI برای دیدن وضعیت factory.
- استفاده از مدل تصمیم‌گیر (مثل Jev) برای مسیریابی مدل یا agent. این مورد بعد از جمع شدن حدود ۲۰–۳۰ package در لاگ بازبینی می‌شود.
- اتصال به issue tracker یا اجرای کاملاً بی‌نظارت.

## ۴. کاربر و سناریوهای اصلی

کاربر: یک مهندس (مالک) که فقط در چت حرف می‌زند و چند پروژه با استک‌های متفاوت دارد.

- **S1 نصب:** مالک plugin را از ریپوی Kargah نصب می‌کند و در یک پروژه‌ی تازه، `kargah init` یا دستور معادل، فایل `.kargah/config.toml` و ساختار لازم را می‌سازد.
- **S2 چرخه‌ی کامل:** `/plan` یک پوشه‌ی plan می‌سازد و `/build` هر package را به ترتیب اجرا و commit می‌کند و یک خط لاگ ثبت می‌شود.
- **S3 ثبت دستی:** وقتی مالک کد را خودش اصلاح می‌کند، با `/rate P3 owner-edit "دلیل"` ثبتش می‌کند.
- **S4 بازنگری:** هفتگی یا بعد از هر plan، مالک `/retro` را اجرا می‌کند، یک پیشنهاد را تأیید می‌کند و بعد از ۱۰ package مقایسه می‌کند.
- **S5 پروژه‌ی چندبخشی:** یک پروژه ممکن است بخش‌های `api`، `ui` و `core` را (هر کدام اختیاری) داشته باشد و Kargah باید با همه‌ی ترکیب‌ها کار کند.

## ۵. اصول طراحی

1. **فقط چیزهای Claude/devchain در plugin.** نیازمندی‌های مخصوص پروژه از template می‌آید، نه plugin.
2. **agent ها عمومی‌اند.** agent ی که به استکی مربوط است ممکن است در یک پروژه استفاده نشود و هزینه‌ای ندارد. دانش مخصوص استک فقط در `AGENTS.md` همان بخش پروژه است، نه در prompt agent.
3. **فایل‌محور و قطعی.** حافظه بین مراحل فایل است. شمارنده‌ها و لاگ را اسکریپت می‌نویسد، نه LLM.
4. **قرارداد روشن و نسخه‌دار.** تغییر ناسازگار یعنی افزایش نسخه‌ی قرارداد و پیام مهاجرت.
5. **مصرف کم.** خروجی `check.sh` حداکثر ۱۰ خط؛ هیچ سرویس دائمی اضافه نمی‌شود.
6. **بهبود فقط با تأیید مالک،** هر بار یک تغییر.

## ۶. قرارداد plugin ↔ پروژه

### ۶.۱ آنچه از plugin می‌آید

- دستورها: `/plan`، `/build`، `/rate`، `/retro`
- agent ها: planner، reviewer، implementer (fallback وقتی Codex به سقف مصرف می‌خورد)
- hook ها: بازیابی context بعد از compact/resume، و hook ثبت لاگ
- اسکریپت‌ها: `pkg-start.sh`، `codex-pkg.sh`، `state.sh`، `log-pkg.sh`
- قالب‌ها: `00-overview.md`، `01-part.md`، `progress.md`، `config.toml`، `log.schema.json`

### ۶.۲ آنچه در پروژه می‌ماند

| آیتم | منبع |
| --- | --- |
| `scripts/check.sh` | template (پروژه) |
| `docs/progress.md` (≤۳۰ خط) | پروژه |
| `docs/kargah-plan/DATE-name/` | پروژه |
| spec ها و ADR ها | پروژه |
| `AGENTS.md` ریشه و `AGENTS.md` هر بخش | پروژه (از template) |
| `CLAUDE.md` | پروژه (حداقل: import از AGENTS.md) |
| `.kargah/config.toml` | پروژه |
| `.kargah/log.jsonl` | پروژه، commit می‌شود |
| `.kargah/state/` (`*.id`، `PLAN-Pn.note`، شمارنده‌ها) | پروژه، در gitignore |

### ۶.۳ قرارداد `scripts/check.sh`

- بدون آرگومان: همه‌ی بخش‌های موجود را اجرا می‌کند.
- با `--layer <api|ui|core>`: فقط همان بخش را اجرا می‌کند.
- خروجی حداکثر ۱۰ خط.
- exit code صفر یعنی موفق و غیرصفر یعنی شکست. plugin به‌جز این به محتوای check وابسته نیست.

### ۶.۴ نسخه‌ی قرارداد

`.kargah/config.toml` فیلد `kargah_contract` دارد. plugin در شروع هر دستور آن را با نسخه‌ی خودش مقایسه می‌کند و اگر ناسازگار بود با پیام روشن و راه مهاجرت متوقف می‌شود.

## ۷. نیازمندی‌های کارکردی

### ۷.۱ ساختار و نصب (PKG)

- **PKG-1:** ریپوی plugin ساختار استاندارد plugin کلاد را دارد (`.claude-plugin/plugin.json`، `commands/`، `agents/`، `hooks/`، `scripts/`، `templates/`).
- **PKG-2:** نصب از طریق `marketplace.json` در همان ریپو ممکن است (GitLab اولویت، GitHub اختیاری).
- **PKG-3:** اسکریپت‌ها با `${CLAUDE_PLUGIN_ROOT}` فراخوانی می‌شوند و هیچ مسیر مطلقی از ماشین مالک در plugin نیست.
- **PKG-4:** plugin هیچ داده‌ی مخصوص پروژه‌ی مالک (نام شرکت، مسیرها، secret) ندارد، چون open-source است.
- **PKG-5:** دستور راه‌اندازی (`init`) فایل‌های لازم پروژه (`.kargah/config.toml`، `log.jsonl` خالی، ورودی gitignore) را از `templates/` می‌سازد و اگر وجود داشتند چیزی را بازنویسی نمی‌کند.

### ۷.۲ دستور `/plan` (PLAN)

- **PLAN-1:** رفتار فعلی حفظ می‌شود: coordinator و planner agent، خروجی `00-overview.md` و `01-part.md`.
- **PLAN-2:** هر ردیف package شامل: شناسه (`Pn` یا `Pna`)، **`layer`** (یکی از `api|ui|core` یا `none`)، حداکثر ۵ فایل و تست پذیرش نام‌دار.
- **PLAN-3:** سؤال‌های باز در `00-overview.md` می‌آید و پاسخ مالک در همان نوشته می‌شود.
- **PLAN-4:** ردیف بدون تست پذیرش یا با بیش از ۵ فایل رد می‌شود و planner دوباره آن را می‌شکند.

### ۷.۳ دستور `/build` (BUILD)

- **BUILD-1:** برای هر package به ترتیب: شروع (از git HEAD، tree تمیز) ← Codex با `codex-pkg.sh` (اول تست شکست‌خورده، بعد کد) ← `check.sh` ← reviewer یک‌بار ← commit با خط `Pkgs:` و بدون push.
- **BUILD-2:** اگر package یک `layer` دارد، `check.sh --layer` اجرا می‌شود و Codex فقط `AGENTS.md` ریشه و همان بخش را دریافت می‌کند.
- **BUILD-3:** وقتی check یا reviewer شکست خورد، آخرین خطوط در `PLAN-Pn.note` نوشته می‌شود و Codex همان session را با note یک دور دیگر ادامه می‌دهد.
- **BUILD-4:** توقف و پرسیدن از مالک: دومین شکست check، `STATUS: blocked/UNCLEAR`، تناقض کد با spec، یا سقف مصرف Codex (در این حالت implementer با sonnet).
- **BUILD-5:** بعد از هر package، `docs/progress.md` (≤۳۰ خط) به‌روز می‌شود.
- **BUILD-6:** باگی که مالک پیدا کند به‌صورت ردیف `P<n>a` زیر همان package ثبت می‌شود (≤۵ فایل، تست مشخص).

### ۷.۴ دستور `/rate` (RATE)

- **RATE-1:** نحو: `/rate <Pn> <outcome> "<دلیل>"`، برای ثبت `owner_edit` و بعداً `escaped_bug`.
- **RATE-2:** دلیل اجباری است؛ اگر خالی بود دوباره پرسیده می‌شود.
- **RATE-3:** رکورد جدید به لاگ اضافه می‌شود و رکورد قبلی package اصلاح نمی‌شود (append-only).

### ۷.۵ لاگ و متریک (LOG)

- **LOG-1:** در مرحله‌ی commit، اسکریپت `log-pkg.sh` یک خط JSON به `.kargah/log.jsonl` اضافه می‌کند. این کار با اسکریپت است، نه با نوشتن LLM.
- **LOG-2:** شمارنده‌ها (تعداد شکست check، دور reviewer، تعداد must-fix/should/nit، تعداد فایل تغییرکرده) را `state.sh` در `.kargah/state/` نگه می‌دارد و `log-pkg.sh` از همان می‌خواند.
- **LOG-3:** فیلدهای هر رکورد:

```json
{
  "schema_version": 1,
  "kargah_version": "0.1.0",
  "plan": "2026-11-05-name",
  "package": "P3",
  "layer": "api",
  "date": "2026-11-05T10:12:00Z",
  "commit_sha": "abc1234",
  "outcome": "clean",
  "check_fails": 0,
  "reviewer_rounds": 1,
  "must_fix": 0,
  "should": 1,
  "nit": 2,
  "files_touched": 4,
  "kind": "feature",
  "stop_reason": null,
  "reason_tag": null
}
```

- **LOG-4:** `outcome` فقط یکی از این‌ها: `clean`، `fixed_after_check`، `reviewer_must_fix`، `stopped_for_owner`، `owner_edit`، و بعداً `escaped_bug`.
- **LOG-5:** `reason_tag` از یک مجموعه‌ی بسته: `spec_unclear`، `test_weak`، `scope_creep`، `env_issue` (و `other` با توضیح کوتاه). مجموعه در `log.schema.json` تعریف می‌شود و اسکریپت تگ نامعتبر را رد می‌کند.
- **LOG-6:** `kind` یکی از `feature` یا `bugfix` است.
- **LOG-7:** `log.jsonl` فقط append می‌شود و هر خط به‌تنهایی JSON معتبر است.

### ۷.۶ دستور `/retro` (RETRO)

- **RETRO-1:** ورودی: `log.jsonl` و تاریخچه‌ی git (join با `commit_sha`).
- **RETRO-2:** رتبه‌بندی بر اساس **تکرار × هزینه** (هزینه = تعداد دور check و reviewer و توقف‌ها).
- **RETRO-3:** حداکثر ۳ پیشنهاد در هر اجرا، هر کدام یکی از: prompt، skill، `check.sh`، قالب plan.
- **RETRO-4:** هر پیشنهاد یک diff روی branch جدا است و هیچ تغییری مستقیم اعمال نمی‌شود.
- **RETRO-5:** گزارش متریک‌های ساده‌ی زیر را نشان می‌دهد: نرخ package های clean، میانگین دور check، میانگین must-fix، نرخ `owner_edit`، نرخ توقف، و همه را به‌تفکیک `layer`.
- **RETRO-6:** وقتی `owner_edit` یا `escaped_bug` بالا باشد ولی must-fix پایین باشد، گزارش هشدار می‌دهد که reviewer احتمالاً ملایم است (محافظت در برابر Goodhart).
- **RETRO-7:** بعد از پذیرش یک تغییر، تاریخ و نسخه‌ی آن ثبت می‌شود تا بعد از ۱۰ package بعدی مقایسه‌ی قبل/بعد با همان متریک‌ها ممکن باشد.

### ۷.۷ hook ها (HOOK)

- **HOOK-1:** بعد از compact یا resume، context از `docs/progress.md`، ردیف جاری plan و `.kargah/state/` بازیابی می‌شود.
- **HOOK-2:** hook ها بدون نیاز به شبکه و با حداقل مصرف اجرا می‌شوند.

### ۷.۸ پشتیبانی از پروژه‌های چندبخشی (LAYER)

- **LAYER-1:** `config.toml` فهرست بخش‌های موجود را دارد (مثلاً `layers = ["api", "core"]`).
- **LAYER-2:** پروژه‌ای با یک بخش یا حتی فقط `core` باید بدون هیچ خطایی کار کند.
- **LAYER-3:** هر package فقط یک `layer` دارد. تغییر چندبخشی به چند package پشت‌سرهم شکسته می‌شود (پیشنهاد، در بخش ۱۰ تصمیم باز است).
- **LAYER-4:** Codex و agent ها `AGENTS.md` ریشه را همراه `AGENTS.md` همان بخش می‌خوانند.

### ۷.۹ مهاجرت از devchain v1 (MIG)

- **MIG-1:** قبل از شروع، نسخه‌ی فعلی با یک tag (`devchain-v1`) فریز می‌شود تا baseline متریک‌ها باشد.
- **MIG-2:** راهنمای مهاجرت تغییر مسیرها را توضیح می‌دهد: `.claude/codex/` به `.kargah/state/`، `docs/devchain-plan/` به `docs/kargah-plan/`، افزودن `.kargah/config.toml` و `log.jsonl`.
- **MIG-3:** پروژه‌ی موجود بدون تغییر رفتار plan و build، یک بار مهاجرت می‌کند و تا آن‌زمان لاگ رکورد نمی‌گیرد.

## ۸. نیازمندی‌های غیرکارکردی

- **NFR-1 سادگی:** هیچ سرویس یا دیتابیس اضافه نمی‌شود؛ فقط فایل، bash/python سبک (با uv) و دستورهای Claude Code.
- **NFR-2 مصرف:** خروجی چاپ‌شده برای Claude در هر مرحله حداکثر ۱۰ خط است.
- **NFR-3 قابلیت اتکا:** اسکریپت‌های `state.sh` و `log-pkg.sh` تست خودکار دارند (bats یا pytest) و در CI ریپوی plugin اجرا می‌شوند.
- **NFR-4 ایمنی:** `log.jsonl` شامل کد، secret یا خروجی خام Codex نمی‌شود، فقط عدد و تگ.
- **NFR-5 قابلیت تکرار:** اجرای دوباره‌ی یک دستور روی حالت نیمه‌تمام (بعد از crash) باید از `.kargah/state/` ادامه دهد و رکورد تکراری در لاگ نسازد.
- **NFR-6 open-source:** مجوز، README، CHANGELOG و مستند قرارداد (`docs/contract.md`) در ریپو وجود دارد.

## ۹. معیار پذیرش

این مرحله وقتی تمام است که همه‌ی موارد زیر درست باشد:

1. plugin روی یک **ریپوی fixture کوچک** (داخل `tests/` خود plugin) نصب می‌شود و یک چرخه‌ی کامل `/plan ← /build` روی یک قابلیت کوچک بدون دست‌کاری دستی تمام می‌شود.
2. بعد از هر package دقیقاً یک خط معتبر (مطابق schema) در `log.jsonl` اضافه شده است.
3. `/rate` یک رکورد `owner_edit` با دلیل ثبت می‌کند و بدون دلیل رد می‌شود.
4. `/retro` روی لاگ نمونه (حداقل ۱۰ رکورد ساختگی) حداکثر ۳ پیشنهاد به‌صورت diff روی branch جدا می‌سازد و چیزی را مستقیم تغییر نمی‌دهد.
5. پروژه‌ی fixture با فقط `core` و پروژه‌ی fixture با `api + ui` هر دو چرخه را تمام می‌کنند.
6. یک پروژه‌ی واقعی مالک از devchain v1 مهاجرت کرده و یک package واقعی را با Kargah تمام کرده است.
7. اسکریپت‌های `state.sh` و `log-pkg.sh` تست دارند و CI سبز است.

## ۱۱. ریسک‌ها

- **داده‌ی کم:** با ۱۰ package نتیجه‌گیری نویزی است؛ برای همین فقط یک تغییر در هر بار و مقایسه‌ی قبل/بعد.
